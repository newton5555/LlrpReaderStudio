# 自研设备开放协议、LLRP 扩展与多厂商兼容项目规划

## 0. 文档定位

本文面向项目规划、技术评审和阶段汇报，说明自研设备未来采用标准 LLRP、厂商扩展、自定义 RShell 及其他标准协议的总体方向。

本文的主角是设备项目及其长期协议路线。现有 LLRPSdk 和 WPF Reader Studio 是前期技术铺路、可行性验证及成果展示平台，不代表固件端已经完成厂商扩展迁移，也不替代后续固件协议设计工作。

本文与《LLRP Reader Studio 标准 LLRP 与多厂商扩展重构规划》相互独立：

- WPF 重构规划解决当前上位机自身的 DataSource、连接生命周期、标准设备接入和能力驱动 UI；
- 本文说明这些基础工作对整个设备项目的价值，以及自研固件未来如何逐步形成“标准 LLRP + 自研厂商扩展”的产品能力。

## 1. 项目现状

### 1.1 自研设备固件

- 当前已经实现标准 LLRP 1.0.1 的基础功能；
- 更完整的设备配置、高级功能和产品差异化能力，仍由一套独立私有协议提供；
- 现有私有协议使用完全不同的报文，不属于 LLRP Custom Message、Custom Parameter 或 Vendor Extension；
- 因此，不能把当前完整私有协议能力描述成“已经支持 LLRP 扩展”。

### 1.2 已完成的技术铺路

现有 LLRPSdk 和 WPF Reader Studio 已经或正在验证四条关键路径：

1. **标准路径可行**：通过标准 LLRP API 连接、识别和操作标准 LLRP Reader；
2. **厂商扩展路径可行**：通过 Impinj Extension 接入厂商特有参数和能力；
3. **多厂商上位机路径可行**：同一个软件可以基于设备身份、标准能力和已安装扩展，兼容不同厂家的 LLRP 设备。
4. **多协议整合路径可行**：WPF 可以在统一设备模型下组合 LLRP、RShell 和其他标准协议提供的能力，而不要求所有功能都通过 LLRP 实现。

这些成果的意义是证明总体技术路线可以落地，并提前准备协议库、扩展框架、设备识别和能力驱动 UI。它们目前是项目的验证基础和展示窗口，不是固件扩展功能已经交付的证明。

## 2. 项目核心判断

项目长期不应在“只支持标准 LLRP”和“继续使用独立私有协议”之间二选一，而应形成分层能力：

```text
设备发现
  使用 mDNS，发现局域网内可用 Reader

通用 Reader 业务能力
  使用标准 LLRP，实现跨厂家基础兼容

厂家差异化能力
  使用规范的 LLRP Vendor Extension

设备管理能力
  固件升级和网络设置参考 Impinj，通过 RShell 实现

通用系统能力
  根据功能优先采用适合的成熟标准协议
```

由此形成面向产品的目标：

> 对外兼容标准 LLRP 设备，对内保留自研设备的差异化能力；同一套上位机既能连接标准设备、加载不同厂家的 LLRP 扩展，也能通过 RShell 和其他标准协议承接设备管理及通用系统功能，而不必为每个厂家复制一套软件。

## 3. 项目目标

### 3.1 近期目标：证明平台兼容能力

- 稳定连接和管理当前 Impinj 设备；
- 支持不依赖 Impinj 扩展的标准 LLRP Reader；
- 根据设备实际能力展示可用功能；
- 用 Impinj Extension 展示厂商扩展可以独立接入，而不会污染标准 LLRP 核心；
- 形成可向项目演示的多厂商设备接入效果。

### 3.2 中期目标：形成可复用的多厂商平台

- 建立统一的设备添加、验证、启用、启动重连和状态展示流程；
- 标准设备、Impinj 设备及未来其他厂家设备使用同一套 DataSource 管理方式；
- 标准功能显示标准设置，厂商特有功能由对应扩展提供；
- 新增一个设备厂家时，以新增适配或扩展模块为主，避免修改公共业务流程；
- 形成设备身份、能力、扩展和固件版本的兼容矩阵。

### 3.3 长期目标：承接自研设备的多协议能力

- 固件继续补齐标准 LLRP 1.0.1 能力；
- 对标准无法表达、又适合通过 Reader 协议开放的功能，设计自研 LLRP Vendor Extension；
- 设备发现使用 mDNS，不依赖指定厂商的扫描机制；
- 固件升级和网络设置从 Reader 业务协议中分离，参考 Impinj 通过自定义 RShell 管理；
- 时间同步、日志、监控、文件传输等通用能力，根据产品需求优先选择成熟标准协议；
- LLRPSdk 增加自研扩展模块；
- 应用层增加 RShell 和其他标准协议的独立服务，不把非 LLRP 协议塞入 LLRPSdk；
- WPF Reader Studio 根据自研设备声明的能力，组合来自不同协议的界面和操作；
- 待替代路径达到功能、兼容性和稳定性要求后，再逐项减少上位机对旧私有协议的依赖。

## 4. 总体产品形态

未来项目可以形成以下组合：

```text
                         同一套 Reader Studio
                                  |
                    mDNS 发现局域网设备
                                  |
               标准连接、能力识别、通用 Reader 操作
                                  |
          +-----------------------+-----------------------+
          |                       |                       |
   标准 LLRP 设备          Impinj LLRP 设备        自研 LLRP 设备
   只使用标准能力          标准 + Impinj 扩展       标准 + 自研扩展

          独立设备管理面            通用标准服务
          自定义 RShell             按功能选择标准协议
          固件升级、网络设置         时间、日志、监控等
```

这里的重点不是让所有设备拥有完全相同的功能，而是让软件遵循统一的接入方式，并根据设备真实能力提供不同功能。

### 4.1 标准设备

- 可以完成标准身份识别、能力查询、配置、盘存和标签操作；
- 不要求安装任何特定厂商扩展；
- UI 只显示该设备实际支持的标准功能。

### 4.2 Impinj 设备

- 先使用标准 LLRP 能力；
- 检测并启用 Impinj Extension 后，显示 Impinj 特有设置和参数；
- 作为“标准核心 + 厂商扩展”模式的现有验证样例。

### 4.3 自研设备

- 当前阶段使用已实现的标准 LLRP 1.0.1 基础能力；
- 完整功能仍由现有独立私有协议承担；
- 通过 mDNS 发布设备发现信息；
- 固件升级和网络设置规划通过自定义 RShell 管理；
- 其他通用功能可按需要采用成熟标准协议；
- 未来固件实现自研 Vendor Extension 后，由同一软件自动识别和展示扩展能力；
- 迁移期间允许标准 LLRP、Vendor Extension、自定义 RShell、其他标准协议和现有独立私有协议并存。

## 5. LLRPSdk 和 WPF 在项目中的角色

### 5.1 LLRPSdk：技术底座与扩展验证平台

LLRPSdk 在本项目中的作用是：

- 提供标准 LLRP 1.0.1/1.1 的消息、参数和高层操作能力；
- 证明标准 Reader 可以通过统一 API 接入；
- 通过现有 Impinj Extension 证明厂商扩展可以模块化接入；
- 为未来自研 Vendor Extension 预留注册、能力查询、配置、盘存和标签报告扩展点；
- 隔离不同厂家协议差异，避免这些差异直接进入上位机页面逻辑。

因此，LLRPSdk 是项目未来协议演进的铺路工程，不等同于固件协议本身。

LLRPSdk 的边界仍然是 LLRP。自定义 RShell 和其他标准协议应由应用层独立服务或独立 SDK 承载，再通过统一设备能力模型与 LLRPSdk 的结果合并。

### 5.2 WPF Reader Studio：多厂商兼容展示与验证平台

WPF Reader Studio 在本项目中的作用是：

- 展示同一个软件连接不同厂家 LLRP 设备的能力；
- 通过 mDNS 发现局域网内可用设备，并把发现结果作为添加 DataSource 的候选信息；
- 验证 DataSource 添加、连接、重连和状态管理流程；
- 根据标准能力和厂商扩展动态呈现设置页面；
- 对声明支持 RShell 管理的设备提供固件升级和网络设置入口；
- 对采用其他标准协议的功能，通过独立能力提供者加载对应状态和操作；
- 为协议、固件和 SDK 联调提供可视化验证入口；
- 将来作为自研设备新扩展能力的首个演示和验收平台。

WPF 的目标不是把所有厂商页面做成完全相同，而是在统一框架内按能力显示差异。

### 5.3 固件：最终能力提供方

固件端决定标准能力和自研扩展能否真正交付，包括：

- 标准 LLRP 功能的完整度和一致性；
- 自研扩展的消息、参数、状态码和能力声明；
- mDNS 服务发布内容和生命周期；
- RShell 固件升级、网络设置及安全访问机制；
- 扩展版本与固件版本兼容规则；
- 与当前独立私有协议的功能边界及迁移节奏。

只有固件、协议定义、SDK 和上位机完成端到端验证后，某项能力才可以被认定为正式支持。

## 6. 自研固件的未来演进原则

### 6.1 按功能选择协议，标准优先

现有私有功能迁移前，先判断功能属于 Reader 业务、设备管理还是通用系统服务，再选择合适协议：

| 功能情况 | 项目处理原则 |
|---|---|
| LLRP 1.0.1 已定义 | 优先补齐或修正固件标准实现 |
| 更高版本标准已定义 | 根据固件版本路线评估升级，不重复设计私有扩展 |
| 标准无法表达的 Reader 业务能力 | 设计自研 LLRP Vendor Extension |
| 固件升级、网络设置 | 参考 Impinj，通过自定义 RShell 管理面实现 |
| 发现、时间、日志、监控、文件传输等通用能力 | 优先评估对应的成熟标准协议 |
| 工厂校准等内部维护能力 | 单独评估是否继续保留内部管理协议 |

### 6.2 不把旧私有报文直接塞进 LLRP

现有独立私有协议可以作为功能需求和行为基线。迁移时不能默认所有功能都变成 Vendor Extension；只有属于 Reader 业务且标准 LLRP 无法表达的功能，才重新定义清晰的 LLRP 扩展语义，包括：

- 厂商标识和消息/参数子类型；
- 请求、响应和异步事件；
- 字段类型、取值范围和错误状态；
- 能力发现和扩展版本；
- 与标准参数的组合方式；
- 向前、向后兼容规则。

这样做才能真正获得 LLRP 生态兼容和统一上位机架构的价值。

### 6.3 按功能逐项迁移

不要求一次替换全部私有协议。推荐以一个完整功能闭环为单位推进：

```text
功能分类
  -> 扩展规范
  -> 固件实现
  -> SDK 支持
  -> WPF 展示
  -> 实机与兼容验证
  -> 决定是否替代旧私有协议路径
```

### 6.4 设备发现使用 mDNS

设备发现统一采用 mDNS，与设备厂家扩展解耦：

- Reader 在局域网发布 LLRP 服务，首选标准 `_llrp._tcp.local.` 服务类型；
- 服务信息可携带设备名称、厂家、型号、序列号、固件版本等必要的非敏感元数据；
- WPF 监听 mDNS 服务并生成候选设备列表；
- mDNS 只表示“发现了设备”，不表示 LLRP 已连接或设备已经通过验证；
- 用户添加设备时仍需执行 TCP 建连、LLRP 握手、身份和能力查询；
- mDNS 不可用时，保留手动输入 IP 或主机名的方式。

### 6.5 固件升级与网络设置使用 RShell

固件升级和网络设置属于设备管理面，不放入标准 LLRP，也不为此设计 Vendor Extension。项目参考 Impinj 的设备管理方式，由自研固件提供符合自身产品需求的 RShell 命令集。

推荐边界：

```text
mDNS
  发现设备和 LLRP 服务

LLRP
  Reader 配置、盘存、标签操作和运行事件

LLRP Vendor Extension
  标准无法覆盖的厂家 Reader 业务能力

自定义 RShell
  固件升级、网络设置和必要的设备维护命令

其他标准协议
  时间同步、日志、监控、文件传输等通用系统能力
```

RShell 方案需要单独定义：

- 安全传输、身份认证、权限和审计；
- 命令、参数、返回码和错误语义；
- 固件包上传、完整性校验、安装、重启、失败恢复和版本确认；
- DHCP/静态地址、网关、DNS 等网络配置模型；
- 网络设置生效后的断线提示、地址变更确认和 mDNS 重新发现；
- 不同型号及固件版本的命令兼容规则。

对第三方设备，Reader Studio 根据该厂家的实际能力决定是否提供固件升级和网络设置；不能假定所有标准 LLRP 设备都支持同一种 RShell 命令。自研 RShell 可以参考 Impinj 的功能边界和交互方式，但命令、认证及兼容规则由本项目独立定义。

### 6.6 其他标准协议的使用原则

对于并非 RFID Reader 专属的通用功能，优先评估成熟标准协议，不在 LLRP Extension 或 RShell 中重复发明已有能力。例如可按实际需求评估时间同步、日志、监控、安全传输和文件传输领域的标准方案。

选择时遵循：

- 协议职责单一，不与 LLRP、RShell 重复提供同一配置入口；
- 优先选择有成熟实现、安全机制和运维工具的标准；
- 固件明确声明服务是否可用、端口、版本和认证要求；
- WPF 通过能力提供者接入，不在 ViewModel 中直接编写各协议客户端；
- 未实现某项标准协议时，不影响设备的标准 LLRP 基础能力；
- 最终采用哪些标准协议，应根据实际功能清单评审确定，本文不提前绑定具体实现。

## 7. 分阶段项目计划

### 阶段一：完成现有展示基线

目标：把已经具备的标准路径和 Impinj 扩展路径稳定展示出来。

主要内容：

- 修复并稳定 Impinj DataSource 添加和连接验证；
- 接入 mDNS 设备发现，同时保留手动地址添加；
- 完善软件启动时已启用设备的连接和 UI 状态更新；
- 分离标准能力与 Impinj 专有能力；
- 准备至少一台 Impinj 设备和一台标准 LLRP 设备的演示场景。

阶段成果：

> 可以现场说明并演示：标准 LLRP 能接入，Impinj 扩展也能接入，同一软件具备兼容多个设备厂家的基础。

### 阶段二：完成多厂商平台化

目标：使“新增设备厂家”从修改整套软件，转变为增加设备识别和厂商扩展模块。

主要内容：

- 统一设备探测、身份识别和能力模型；
- 建立 Extension Resolver 和扩展注册机制；
- 建立独立的设备管理能力模型，区分 LLRP 业务能力和 RShell 管理能力；
- 设置区按能力显示、约束、增加或替换设置项；
- 通用 Inventory、Tag Report 和 Tag Access 与厂商差异解耦；
- 建立设备型号、固件和扩展兼容矩阵。

阶段成果：

> Reader Studio 成为一个能力驱动的多厂商 LLRP 上位机，而不是 Impinj 专用工具。

### 阶段三：选择自研多协议能力试点

目标：验证自研设备能够按职责同时使用 LLRP Extension、RShell 和适用的标准协议，并由同一 WPF 统一呈现。

主要内容：

- 完成现有私有功能与标准 LLRP 的对照；
- 选择一个适合 Vendor Extension 的 Reader 业务试点功能；
- 选择固件升级或网络设置作为自定义 RShell 试点；
- 如功能清单中存在适合的通用能力，再选择一个标准协议接入试点；
- 分别定义协议、版本、能力声明和测试向量；
- 完成固件、协议客户端或 LLRPSdk 扩展、应用服务和 WPF UI；
- 与旧私有协议进行结果一致性和稳定性验证。

阶段成果：

> 不再只用 Impinj 证明别人家的扩展可行，而是用自研设备证明项目自身具备标准协议选型、自定义 RShell、LLRP Vendor Extension 和多协议统一展示能力。

### 阶段四：按产品价值逐步替代旧私有功能

目标：根据试点结果和产品优先级，为每项旧私有功能选择标准 LLRP、Vendor Extension、自定义 RShell、其他标准协议或继续保留的合理归属。

主要内容：

- 建立标准能力补齐清单；
- 建立 Vendor Extension 候选清单；
- 建立自定义 RShell 功能清单；
- 建立其他标准协议承载功能清单；
- 建立继续保留独立协议的功能清单；
- 实现并验证自研设备的 mDNS 服务发布；
- 分阶段实现 RShell 固件升级和网络设置；
- 按型号和固件版本发布扩展；
- 在满足兼容性和稳定性要求后，逐步减少新上位机对旧私有业务协议的依赖。

## 8. 项目演示建议

项目阶段汇报不应只展示代码结构，建议用三类设备场景说明路线：

| 演示场景 | 要证明的内容 |
|---|---|
| 标准 LLRP Reader | 不依赖厂商扩展也可以完成通用连接和操作 |
| Impinj Reader | 在标准能力基础上，可以加载成熟的第三方厂商扩展 |
| 自研 Reader | 当前标准能力可以接入；未来可沿同一机制加载自研扩展 |

建议演示顺序：

1. 在同一 DataSource 页面添加不同厂家设备；
2. 演示通过 mDNS 自动发现设备，也可以手动输入地址；
3. 展示统一的连接、启用和运行状态；
4. 展示所有设备共有的标准设置；
5. 切换到 Impinj 设备，展示根据扩展能力出现的专有设置；
6. 展示固件升级和网络设置属于独立 RShell 管理入口；
7. 说明自研固件未来扩展将复用同一接入机制，而不需要再开发一套独立上位机框架。

## 9. 项目收益

### 9.1 对产品

- 形成“支持标准 LLRP”的基础兼容能力；
- 上位机可兼容 Impinj、自研设备和其他标准 LLRP 厂家；
- 自研设备可通过规范扩展、自定义 RShell 和其他标准协议提供更加完整的功能；
- 降低项目被单一设备厂家或单一私有上位机绑定的风险。

### 9.2 对研发

- 标准功能、厂家扩展和 UI 职责边界更清楚；
- 新增厂家或型号时复用公共连接和业务流程；
- 固件和上位机可以围绕统一能力模型联调；
- 扩展版本、设备能力和错误状态可以测试和追踪。

### 9.3 对项目展示与合作

- 可以明确展示项目具备标准协议接入能力；
- 可以用 Impinj 证明成熟厂商扩展能够被兼容；
- 可以说明自研设备未来扩展已有承接平台，而不是从零开始；
- 为后续第三方设备适配、客户集成和生态合作提供统一技术口径。

## 10. 范围边界

本规划不表示：

- 当前自研设备已经实现完整 LLRP Vendor Extension；
- 当前独立私有协议属于 LLRP 扩展；
- 所有私有功能都必须迁移到 LLRP；
- 自研设备只能通过 LLRP 和 Vendor Extension 提供全部功能；
- LLRPSdk 或 WPF 可以代替固件端协议开发；
- 多厂商兼容意味着不同设备的全部功能完全一致。
- 固件升级和网络设置属于标准 LLRP 或 LLRP Vendor Extension。

本规划表示：

- 标准 LLRP 接入路径已经具备基础；
- Impinj 已证明厂商扩展接入模式可行；
- WPF 正在形成多厂商、能力驱动的统一展示平台；
- 项目明确采用 mDNS 发现设备，并以 RShell 承载固件升级和网络设置；
- 自研设备可以按功能组合自定义 RShell 和其他成熟标准协议；
- 项目已经为自研固件未来采用规范 Vendor Extension 做技术铺路；
- 后续是否迁移、迁移哪些功能及何时迁移，需要设备项目单独立项和评估。

## 11. 项目验收指标

### 11.1 平台铺路阶段

1. 同一软件可以添加并管理标准 LLRP 和 Impinj 设备；
2. 标准功能不依赖 Impinj Extension；
3. Impinj 扩展失败不会破坏标准 LLRP 基础路径；
4. UI 根据实际能力显示功能，不依赖写死的型号判断；
5. 添加、启用、软件重启和连接失败状态符合统一规则；
6. mDNS 发现与手动地址添加都可用，发现结果不会被误判为已连接；
7. LLRP Reader 业务与 RShell 设备管理具有清晰边界；
8. 新设备厂家的适配点有明确边界。

### 11.2 自研扩展试点阶段

1. 明确证明试点功能无法由现有标准合理表达；
2. 固件能够声明扩展身份、版本和能力；
3. LLRPSdk 能够独立加载自研扩展；
4. WPF 能够根据能力显示对应功能；
5. 新扩展与旧私有协议的功能结果一致；
6. 未安装扩展或版本不兼容时，标准 LLRP 功能仍可使用；
7. 完成跨固件版本、异常断线和长时间实机验证。

### 11.3 设备管理与发现阶段

1. 自研设备能够稳定发布和撤销 mDNS 服务；
2. 地址变化或设备重启后，Reader Studio 能重新发现设备；
3. RShell 的认证、权限、错误码和操作日志满足项目安全要求；
4. 固件升级具备包校验、过程状态、失败恢复和升级后版本确认；
5. 网络设置修改后，UI 能提示连接中断并通过 mDNS 找回设备；
6. 其他标准协议服务与设备能力声明一致，服务不可用时不会影响 LLRP 基础路径；
7. 不支持 RShell 的第三方设备不会显示不可用的管理入口。

## 12. 工作量与立项建议

当前 LLRPSdk 和 WPF 的标准化、多厂商重构属于平台铺路工作，可以独立推进并用于项目展示。

自研私有功能迁移则涉及固件、协议规范、编解码、SDK 扩展、WPF 接入和实机验证，不能包含在单纯的 WPF 重构工作量中。建议在平台基线稳定后，先用一个功能做独立试点，再根据结果估算后续批量迁移成本。

正式估算前至少需要三份清单：

- 标准 LLRP 已支持、部分支持和未支持功能清单；
- 当前独立私有协议功能清单；
- 标准补齐、Vendor Extension 候选和继续保留独立协议的分类清单。

## 13. 项目统一表述

### 13.1 简短汇报版本

> 当前自研设备已经具备基础 LLRP 1.0.1 能力，完整高级功能仍使用独立私有协议。我们正在通过 LLRPSdk 和 Reader Studio 做技术铺路：标准 LLRP 设备可以接入，Impinj 的厂商扩展也可以接入，同一软件将能够兼容多个设备厂家。未来自研设备不要求把全部功能都迁入 LLRP，而是按职责组合标准 LLRP、Vendor Extension、自定义 RShell 和其他成熟标准协议：mDNS 负责发现，LLRP 负责 Reader 业务，RShell 负责固件升级和网络设置，其他通用能力优先采用合适的标准协议。

### 13.2 技术评审版本

> 项目采用“mDNS 设备发现 + 标准 LLRP 核心 + 可插拔厂商扩展 + 自定义 RShell 设备管理 + 其他标准协议 + 能力驱动上位机”的演进方向。现阶段 LLRPSdk 和 WPF 用于验证标准设备、Impinj 扩展及多厂商统一接入，不把现有独立私有报文误称为 LLRP 扩展。后续先按功能职责完成协议分类：Reader 通用业务优先标准 LLRP，厂家 Reader 业务采用 Vendor Extension，固件升级和网络设置采用自定义 RShell，通用系统功能优先选择成熟标准协议。各路径端到端验证后，再决定旧私有协议的逐项替代范围。

## 14. 最终结论

现阶段项目已经通过 LLRPSdk 和 WPF Reader Studio 为未来路线完成关键铺垫：

- 标准 LLRP 可以作为多厂家兼容的共同基础；
- Impinj 证明厂商扩展可以在标准基础上独立接入；
- 同一套上位机可以根据设备能力兼容不同厂家，而不必复制多套软件；
- mDNS 负责设备发现，LLRP 专注 Reader 业务，自定义 RShell 负责固件升级和网络设置，其他通用能力优先采用成熟标准协议；
- 自研固件未来可以在补齐标准能力的同时，把适合的差异化功能逐步迁移为规范的 LLRP Vendor Extension；
- 现有独立私有协议在替代完成前继续承担当前产品功能，每项功能根据职责选择新协议或继续保留，不追求用单一协议覆盖全部能力。

因此，当前 LLRPSdk 和 WPF 工作的项目价值，不是宣称固件扩展已经完成，而是证明路线、建立底座、展示多厂商兼容能力，并显著降低未来自研扩展落地的技术风险。
